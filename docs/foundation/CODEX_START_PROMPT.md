## Реализуй первый законченный инкремент

Нужна одна проверяемая цепочка: пользователь создает observation → загружает один primary photo → создает assessment с idempotency key → получает 202 → worker выполняет устойчивую задачу → клиент читает неизменяемый результат. Предварительно согласованные состояния и поля берутся из API_CONTRACT; согласуй Pydantic/OpenAPI, БД, runtime и generated TS client.

Система — модульный монолит с отдельными процессами API и worker. PostgreSQL хранит durable jobs; claim короткий, inference вне транзакции; lease token защищает финализацию от устаревшего worker. Повторная отправка того же запроса не создает дублей. Assessment и job создаются атомарно. Версия bundle закрепляется в момент создания запроса. Нужны bounded retries, восстановление после остановки worker и явная техническая ошибка после исчерпания попыток.

Модули организуй по функциям, с простыми router/schema/service/model. Внешние ImageStore и Predictor — небольшие порты с адаптерами. Не добавляй универсальные BaseRepository/BaseService, Kafka, Kubernetes, event sourcing или отдельный ML microservice без конкретной необходимости.

ML-runtime не импортирует FastAPI/ORM/training. Model bundle включает checksum, ordered label IDs, input/preprocessing/postprocessing, supported crop-condition-organ, score space, calibration/threshold policy и provenance. Если настоящего проверяемого bundle нет, production path возвращает документированную недоступность модели. Тестовая заглушка допустима только в тестах или явно включенном dev режиме; она никогда не выглядит для пользователя как фактическая диагностика.

В первой итерации фото ограничено по байтам и числу пикселей, фактически декодируется, приводится по EXIF/RGB, хранится приватно и неизменяемо после ready. Проверяй ownership всех связанных объектов, включая photo ID, polling и download. UUID не является разрешением. Не включай фото пользователей, секреты и датасеты в Git.

## Мобильный клиент

Собери основной поток по Figma: https://www.figma.com/design/07cVYgjO4tZw4IaR7kUxEz

Реализуй выбор культуры из реального supported manifest, съемку или выбор изображения, preview, отправку, processing и результат/ошибку. Предсказание — гипотеза. Отличай processing status `queued/running/completed/failed` от completed outcome `predicted/inconclusive/unsupported_input/retake_photo`. Предварительный отказ API и завершенный результат модели — разные ветки; следуй контракту.

Результат без достаточных оснований не называй healthy. Выбор культуры не должен превращать маленькие глобальные scores в уверенный диагноз после скрытой перенормировки. Пользовательский комментарий не перезаписывает prediction и не становится ground truth. Offline capture/upload queue реализуй отдельным следующим инкрементом после стабильной online-цепочки; не выдавай сохранение черновика за offline inference.

## Проверка инкремента

Проверь именно существенные свойства: успешный цикл; запрет доступа пользователя B к фото/истории/assessment пользователя A; повтор идемпотентного запроса и конфликт тела; остановка worker после claim и перед commit; отказ устаревшей lease; неверный файл/превышение лимита; manifest label-order/preprocessing mismatch; отсутствие модели. Для настоящего bundle добавь PyTorch/ONNX parity на фиксированных fixtures. Не подменяй эти проверки тестами, которые просто повторяют реализацию.

Версии Python/PyTorch/CUDA/ONNX и Expo/RN выбирай по официальной совместимости и фактическому окружению, затем фиксируй locks. Не ставь случайные latest версии всех пакетов. GPU-обучение не должно требоваться для локальной проверки API.
