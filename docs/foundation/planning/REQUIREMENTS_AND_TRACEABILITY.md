# AgroVision — технические требования и методы проверки

Историческая проектная спецификация от 21 октября 2026. Приоритеты M (Must) и S (Should) описывают предлагаемый объем, а не выполненные проверки. Актуальная реализация и измерения: [IMPLEMENTATION](../../development/IMPLEMENTATION.md), [DATA_AND_MODEL](../../development/DATA_AND_MODEL.md), [MOBILE_REPORT](../../development/MOBILE_REPORT.md). Offline и web не входят в текущий online MVP.

## 3. Границы и роли

**Фермер / растениевод:** снимает лист поддерживаемой культуры, получает предварительную оценку, видит ограничения, сохраняет наблюдение и историю. Интерфейс и рабочие гипотезы еще должны быть проверены обсуждениями с такими пользователями.

**Эксперт по растениям / разметчик:** проверяет разрешенные для исследования фотографии и фиксирует референсные метки с уровнем подтверждения. Наличие эксперта, лаборатории или договора не предполагается автоматически. Эксперт не обязан быть оператором инфраструктуры.

**Технический оператор / ML-исследователь:** проверяет и выпускает модельные артефакты, запускает воспроизводимую оценку, контролирует сбои. На первом этапе допустим CLI; отдельная большая админ-панель не обязательна.

Начальная граница данных — владелец `owner_user_id`. Полноценная enterprise tenancy, подписки, организации и приглашения не требуются. Если реальные интервью подтвердят совместный доступ к одной ферме, выбрать небольшую membership-модель отдельно; не реализовывать обе модели владения параллельно.

Вне первой версии: универсальное распознавание любых растений, автоматическое установление причины болезни по региону, прогноз переноса инфекции ветром, обязательная GIS-платформа, on-device inference, автоматическая агрономическая экспертиза, B2B-биллинг. Включение нового объема требует требования и проверки, а не только строки в презентации.

## 4. Функциональные требования

Обозначения тестов ниже описывают **запланированные проверки**, не существующие файлы и не пройденные тесты. Каждый критерий приемки относится к будущей реализации.

|---|---|---|---|
| **FR-01 M** | Система публикует явный каталог поддерживаемых культур, состояний и органов растения. | Исследуемая multi-crop конфигурация включает не менее двух культур. Каждая поддержанная пара «культура–состояние» связана с модельной версией и отчетом. Mobile получает стабильные IDs из API; будущий web использует тот же контракт; неподдержанный `crop_id` не запускает обычную классификацию. Конкретные культуры выбираются по данным, не выдумываются ради числа. | `catalog`, `assessments/model-selection`, `api-client`; **T-CAT**, **T-MOD** |

При последующем добавлении web он обращается к той же identity/history; web-приемка не входит в текущий mobile scope. Выход отзывает соответствующую refresh-сессию; повторное обновление с отозванным credential отклоняется. | **FR-03 M** | Пользователь создает наблюдение с фотографией, выбранной культурой и метаданными съемки. | Для выбранной поддерживаемой культуры можно сохранить одно фото, орган/дату и необязательную заметку. `client_observation_id` повторного запроса не создает второе наблюдение. | **FR-04 M** | Система принимает и проверяет фото до выполнения assessment. | Предлагаемый входной контракт: JPEG/PNG, не более 10 MiB и 20 мегапикселей; пороги конфигурируемы и отражены в UI/API. | **FR-05 M** | Пользователь запускает одну оценку готового фото с безопасным повтором запроса. | `POST /v1/assessments` после durable commit возвращает ID и `202`. Два параллельных запроса с одним владельцем, ключом и телом дают один assessment/job. Повтор с тем же ключом и другим телом дает `409`. Фото другого владельца не принимается. | `assessments`, DB transaction, `identity`; **T-JOB**, **T-AUTH** |
| **FR-06 M** | Пользователь видит состояние выполнения; задача переживает кратковременный сбой worker. | API различает `queued`, `running`, `completed`, `failed`. Перезапуск worker не оставляет задачу бессрочно в `running`; lease recovery и ограниченные retries приводят к одному сохраненному результату либо явной ошибке. UI показывает ожидание и возможность повторить разрешенное действие. | `assessments/jobs`, worker, web/mobile result; **T-JOB**, **T-RES**, **T-UI** |
| **FR-07 M** | Результат честно различает поддержанную гипотезу и недостаточность данных. | Контракт и UI поддерживают `predicted`, `inconclusive`, `unsupported_input`, `retake_photo`. Есть причина/следующее действие. `predicted` содержит стабильную пару «культура–состояние» и версию модели. Имеются примеры здорового класса, неуверенности, неподдержанного ввода и плохого фото; ошибки сервера отображаются отдельно. Model score не подписывается как проверенная вероятность правильного диагноза. | `assessments/decision-policy`, `catalog`, clients; **T-RES**, **T-UI**, **T-EVAL** |
| **FR-08 S** | Пользователь получает краткую справку о поддержанном состоянии и ограничениях вывода. | Для справки указаны версия/источник; отображаются название, объяснение предварительного характера оценки и применимое следующее действие. При неизвестном результате доступна помощь по пересъемке/обращению к специалисту. Текст справки отделен от численного вывода модели. | `catalog/content`, result UI; **T-RES**, **T-UI**, контент-review |
| **FR-09 M** | Пользователь просматривает собственную историю и детали наблюдений. | История пагинируется, фильтруется минимум по дате и культуре; карточка показывает фото, исходные метаданные и assessment-версии. Повторный запуск новой модели создает отдельную запись и сохраняет старый результат. Объекты другого владельца не появляются в выдаче. | `observations`, `assessments`, clients; **T-OBS**, **T-MOD**, **T-AUTH** |
| **FR-10 S** | Пользователь связывает наблюдения с фермой, полем и сезоном. | Можно создать `Farm`, `Field`, `FieldSeason` с культурой сезона и связать наблюдение со своим сезоном. Изменение культуры нового сезона не меняет прошлые наблюдения. Все ссылки проверяют владельца. Полигональная карта не требуется. | `farms`, `observations`; **T-OBS**, **T-AUTH** |
| **FR-11 S** | Mobile сохраняет offline-черновики и отправляет их после восстановления связи. | Без сети фото и метаданные сохраняются в постоянном хранилище приложения; после обычного перезапуска и восстановления связи пользователь может продолжить. Повторы используют прежние IDs/keys и не создают дублей. Смена аккаунта не отправляет черновик первого пользователя от имени второго. До серверного результата UI показывает pending, а не диагноз. | mobile draft queue/files/SQLite, `api-client`; **T-OFF**, **T-JOB**, **T-AUTH** |
| **FR-12 S** | Пользователь оставляет отзыв о конкретном результате. | Отзыв связан с assessment и автором, сохраняется/читается по разрешениям. Сообщение «неверно» или выбранная пользователем метка не меняют prediction и не получают автоматически статус экспертной разметки. | `feedback`, clients; **T-ANN**, **T-AUTH** |
| **FR-13 S** | Эксперт фиксирует отдельную исследовательскую аннотацию разрешенного образца. | В записи есть образец, культура/состояние или `uncertain`, источник и уровень подтверждения, автор и время. Эксперт имеет доступ только к назначенной/разрешенной выборке. Экспорт сохраняет provenance; визуальное мнение не становится лабораторным подтверждением без соответствующего основания. Допустим простой интерфейс или управляемый импорт таблицы. | `feedback/annotations`, research export; **T-ANN**, **T-AUTH** |
| **FR-14 M** | Оператор проверяет и активирует версионированный модельный bundle. | Проверяются checksum, manifest, label-order, preprocess/postprocess, runtime, status/совместимость decision policy и score space; calibration artifact обязателен при заявленной calibration. Null thresholds не считаются разрешающими defaults. Некорректный bundle не активируется. Новый активный bundle используется новыми запросами; созданные ранее задачи сохраняют исходную версию. Возможен возврат к прежнему проверенному bundle. CLI достаточен. | `assessments/model-registry`, `ml/runtime`, operator CLI; **T-MOD**, **T-JOB** |
| **FR-15 S** | Пользователь удаляет собственное наблюдение и связанные доступные данные. | После удаления наблюдение отсутствует в истории; новые обращения и новые download URLs отклоняются. Worker не публикует результат для удаленного наблюдения. Приватные blob-объекты удаляются по документированному cleanup-процессу; ранее выданная signed URL действует не дольше ее настроенного TTL. | `observations`, `assessments`, storage cleanup; **T-DEL**, **T-AUTH**, **T-JOB** |
| **FR-16 M** | ML-исследователь запускает воспроизводимую оценку и сохраняет отчет. | Одна документированная команда/процедура использует зафиксированные dataset manifest, групповой split, model bundle и конфигурацию. Отчет содержит baseline на том же split, class/crop metrics, confusion matrix, abstention coverage и ошибки на неподдержанном/неподходящем вводе, сведения об оборудовании и версиях. Отсутствующие локальные данные явно отражены в выводах. | `ml/training/evaluation`, manifests/reports; **T-EVAL**, **T-REPRO** |

Наличие `Should`-интерфейса не мешает готовить его данные/контракт в архитектуре. Например, схема `FieldSeason` может быть предусмотрена до полноценного UI управления фермой, а исследовательская разметка — в таблице до создания экспертной панели.

## 6. Реестр методов проверки

| Test ID | Что проверяется | Материал / наблюдаемое доказательство |
|---|---|---|
| T-CAT | Каталог и model capabilities | Контрактные ответы; минимум две выбранные культуры; отвергнутые неизвестные IDs; manifest ↔ API consistency |
| T-AUTH | Учетная запись и доступ к объектам | Два тестовых пользователя; матрица разрешенных/запрещенных операций; logout/refresh; фото/результаты/поля/annotations |
| T-OBS | Наблюдение, история, поля/сезоны | Создание/чтение/фильтр/пагинация; same-client-ID; смена сезона без изменения старых записей |
| T-UPL | Upload lifecycle | Валидные фото, неверное расширение/MIME, поврежденный файл, размер/pixels сверх лимита; незавершенная загрузка не ready |
| T-JOB | Durability/idempotency | Конкурентные одинаковые запросы, измененное тело с прежним ключом, kill/restart, lease expiry/fencing, retry exhaustion |
| T-RES | Состояния и контракт результата | Зафиксированные примеры всех outcomes и технических ошибок; generated TS compatibility |
| T-UI | Пользовательский end-to-end | Текущий mobile-путь: вход, выбор, фото, ожидание, результат, история; error/retake branches. При добавлении web — повторная приемка для web |
| T-OFF | Offline и повторная отправка | Сохранение файла/очереди, закрытие процесса, потерянный HTTP-ответ, повторный upload, смена аккаунта, storage full |
| T-ANN | Feedback и reference labels | Раздельные записи, права эксперта, `uncertain`, review provenance, export без подмены predictions |
| T-MOD | Модельный bundle и release | Hash/manifest/labels/runtime validation; queued-job pinning; rejected invalid release; rollback |
| T-DEL | Удаление и фоновые гонки | Запрет новых чтений/URL, отсутствие новых results после удаления, cleanup, истечение старых URLs |
| T-EVAL | Качество и baseline | Одна процедура, единый split, per-class/per-crop metrics, confusion, coverage и неподдержанный ввод |
| T-REPRO | Повторимость | Зафиксированные versions/manifests/configs; повторный запуск и export parity с объявленным допуском |
| T-PERF | Производительность | 100 изображений, два одновременно активных запроса, CPU/RAM/threads/version, cold/warm отдельно |
| T-UX | Формативная usability-проверка | Реальные 5 участников, сценарий/время/ошибки, изменения; никаких синтетических «отзывов пользователей» |
| T-CI | Сборка и границы пакетов | Run logs из чистого checkout, locked dependencies, contract drift, meaningful integration checks |

## 7. Реалистичные сценарии

### SC-01. Растениевод проверяет лист выбранной культуры в mobile

**Предусловие:** пользователь вошел; культура есть в поддерживаемом каталоге. **Цель:** получить предварительную оценку конкретного фото и сохранить наблюдение.

1. Пользователь выбирает культуру и делает/загружает одно фото листа.
2. UI сообщает требования к кадру и размеру. Farm/field association остается необязательной.
3. Фото проходит проверку, сервер создает assessment и показывает ожидание.
4. Пользователь получает поддержанный результат либо честную неопределенность, видит следующее действие.
5. Наблюдение доступно в собственной mobile-истории; указана модельная версия. Тот же контракт предусмотрен для будущего web-клиента.

Связи: FR-01–07, FR-09; NFR-02/04/06/08. Этот сценарий не обещает лабораторное подтверждение или точность на всех растениях Казахстана.

### SC-02. Фото непригодно либо культура не поддержана

Если выбранная культура уже известна как неподдерживаемая, UI объясняет ограничение до отправки на анализ; прямой `POST /v1/assessments` получает HTTP `422 unsupported_crop`, без создания assessment/job. Известную каталоговую культуру с `can_assess: false` можно сохранить как observation/photo без оценки. Если файл невозможно декодировать или превышен лимит, upload отклоняется отдельной ошибкой входа; inference также не начинается.

Если допустимый файл уже принят для поддерживаемой культуры, обработка может завершиться с outcome `retake_photo` при выявленном непригодном качестве, `unsupported_input` при обоснованно выявленном входе вне поддерживаемой области либо `inconclusive` при недостатке оснований для вывода. Это completed results существующего assessment; они не смешиваются с preflight HTTP 422. Пользователь может выбрать поддерживаемую культуру или сделать другое фото. Технический `failed` показывает иной текст и действие. Низкая уверенность не конвертируется в случайный диагноз. Один assessment использует одно основное фото; дополнительные контекстные снимки не объединяются моделью в v1.

Связи: FR-01/04/07/08; T-CAT/T-UPL/T-RES. Не предполагается, что threshold автоматически обнаруживает все чужие виды растений: это отдельная проверяемая ML-гипотеза.

### SC-03. На участке нет сети

Пользователь делает фото в native-приложении и видит «сохранено на устройстве; ожидает отправки». После закрытия и открытия приложения draft остается. При связи он отправляется с тем же идентификатором. Если первый ответ сервера потерян, retry получает прежний assessment, не создает второй. Если пользователь сменил аккаунт, старый draft не отправляется от имени нового пользователя. До ответа сервера диагноз не показывается.

Связи: FR-03/05/06/11; NFR-03/09; T-OFF/T-JOB/T-AUTH.

### SC-04. Пользователь ведет историю по одному полю

Пользователь создает поле и сезон с выбранной культурой, прикрепляет несколько собственных наблюдений разных дат, фильтрует историю и открывает исходные фото/результаты. Следующий сезон может иметь другую культуру без изменения прошлых записей. История показывает наблюдения; из нескольких фотографий не выводится неподтвержденная статистика зараженности всей фермы или прогноз распространения.

Связи: FR-09/10; T-OBS/T-AUTH.

### SC-05. Эксперт проверяет исследовательский образец

Эксперт открывает разрешенный образец и доступные исходные метаданные. Он указывает культуру/состояние или `uncertain`, метод и уровень подтверждения. Результат модели остается неизменным. В исследовательский экспорт попадают метка, provenance и group IDs. Если оснований недостаточно, образец не объявляется надежным референсом только для увеличения размера обучающего набора.

Связи: FR-12/13/16; NFR-01/04/06; T-ANN/T-EVAL. Для независимой разметки полезно скрывать прогноз модели до первичного экспертного решения; это предлагаемый прием против смещения, не утверждение о проведенной процедуре.

### SC-06. ML-оператор выпускает новую модель

Оператор выполняет фиксированную процедуру оценки baseline и кандидата, проверяет bundle и сохраняет отчет. После активации новые assessments получают новую версию; уже поставленные в очередь исполняются с прежней. При проблеме кандидат отклоняется либо активная версия возвращается к ранее проверенной. Старые результаты и их версии сохраняются.

Связи: FR-14/16; NFR-01/03/06/10; T-MOD/T-EVAL/T-JOB. Отдельная большая админ-панель для этого не требуется.

## 8. UML Use Case: актеры, варианты использования и связи

### Актеры

- `Farmer`: растениевод / обычный пользователь.

Все роли являются проектными. Не утверждать, что реальные внешние эксперты уже привлечены. `Expert` и `Operator` не наследуют друг друга автоматически.

## 9. Контекстная и компонентная схемы: узлы и корректные границы

### Контекстная схема

Центральная граница: **AgroVision — система наблюдений и предварительной оценки фото растений**.

Внешние участники/источники:

1. Растениевод — фото, выбранная культура, наблюдение/поле; обратно состояние, предварительная оценка, история.
2. Эксперт — разрешенные фото/метаданные; обратно reference annotations с уровнем подтверждения.
3. Технический оператор/ML-исследователь — конфигурации/релизы; обратно отчеты оценки/ошибки эксплуатации.
4. Проверенные датасеты и локальные исследовательские образцы — источник для offline training/evaluation. Это данные с provenance, не предположение об автоматическом live API.

PostgreSQL/S3/ONNX — внутренние компоненты, поэтому подробно показывать их на компонентной схеме, а не выдавать за бизнес-пользователей. Внешний identity provider рисовать только если такой вариант действительно выбран. Погода/GIS/ветровые API не входят в текущий утверждаемый объем.

### Компонентная схема

Проектируемые узлы:

- React web UI.
- React Native / Expo UI и local draft storage.
- Shared TypeScript API client/types — зависимость при сборке, не отдельный сетевой сервис.
- FastAPI HTTP process: identity, catalog, observations/farms, assessments, feedback.
- Inference worker process **из того же server codebase**, использующий assessment service.
- PostgreSQL: metadata, ownership, results, model-version metadata, `assessment_jobs`.
- Private S3-compatible object storage: ready photos и versioned model bundles.
- `ml/runtime` — локальная библиотека worker: preprocessing, ONNX session, postprocessing.
- Offline training/evaluation tooling: datasets/manifests, training, baseline, evaluation, bundle export.

Связи и подписи:

| Откуда → куда | Смысл |
|---|---|
| Web / Mobile → FastAPI | HTTPS REST `/v1`, auth, uploads, polling, history |
| API client/types → Web / Mobile | Build-time generated contract/code dependency; пунктирная связь |
| FastAPI → PostgreSQL | Authorized reads и transaction: assessment + job |
| FastAPI → Object storage | Private upload / authorized download URL |
| Worker → PostgreSQL | Claim/lease/retry/fenced result commit |
| Worker → Object storage | Load ready photo and pinned model bundle |
| Worker → `ml/runtime` | Local library call, не HTTP |
| Training/evaluation → bundle storage | Controlled export of immutable artifact + report |
| Model metadata ↔ PostgreSQL | Active-version selection and exact pinned IDs; это таблицы/модуль, не новый registry-microservice |

Для компактного рисунка сгруппировать API+worker как одно backend application с двумя процессами; внутри сохранить различимость. Training/evaluation показать отдельно от serving. Сеть, локальный вызов и перенос артефактов не обозначать одной нерасшифрованной стрелкой.

### Минимальная трассировка схем

`UC-03 → FR-03/04/05 → UI + observations + storage + assessments → T-UPL/T-JOB`.

`UC-04 → FR-06/07 → API + worker + ml/runtime + results → T-JOB/T-RES`.

`UC-09 → FR-13 → annotation data → T-ANN`.

`UC-10/12 → FR-14/16 → offline ML + bundle + model metadata → T-MOD/T-EVAL`.
