## 1. Два разных результата

**К 24 октября** подготовить и проверить исследовательско-проектный пакет: proposal, доказательства актуальности, литературу, аналоги, технические сравнения, требования, архитектуру, mobile-прототип, план оценки, управление проектом и отзыв руководителя. ML сравнивается на фиксированных данных и переносе между условиями. Web остаётся следующей фазой; его UI и код сейчас не разрабатываются.

### Критические зависимости

ML-путь: **аудит данных → manifest/splits → feasibility → сравнение backbone → calibration/отказы → bundle → локальная оценка**. Backend-путь: **схемы/доступ → upload/history → durable job → mobile integration → recovery/ownership tests**. Они соединяются на согласованном API и model bundle.

Если локальные данные недоступны, software и публичный benchmark могут продолжаться. Итоговый статус при этом — исследовательский прототип для дальнейшей проверки в Казахстане. Диагностический выпуск не открывается посредством ослабления порога, удаления теста или формального переименования датасета.

## 5. Что делать при нехватке времени

Сначала сохранять целостность основного пути: один снимок, выбранная культура, устойчивый assessment, объяснимое состояние результата, история, воспроизводимый ML-отчёт. Отложить необязательные модельные расширения, detector/segmentation, DINO/ConvNeXt эксперименты, on-device inference, iOS без доступного устройства и web UI.

Управление фермами/полями, пользовательский feedback и экспертная панель остаются отдельными Should-расширениями; необходимая исследовательская разметка может выполняться управляемой таблицей. Offline draft запланирован в AGRO-024, но при переносе эта функция явно исключается из заявленного MVP, а её проверки удаляются только из текущей приёмки с записанным решением. Нельзя описывать непротестированную функцию как выполненную.

Изменение scope записывается в задаче и decision log: причина, что переносится, какие FR/NFR затронуты, новый критерий этапа, reviewer. При этом не удаляются неудобные экспериментальные результаты и не ослабляются пороги после просмотра final test.

## 7. Простой Git/YouTrack-процесс для двух человек

### Перед первой задачей

Сохранить текущую работу обоих участников; выбрать один продолжающийся репозиторий. Каждый использует собственный аккаунт и собственные `user.name`/`user.email` в Git. Не настраивать чужое авторство и не создавать задним числом искусственную историю. Git хранит имя и email в commits; область настроек может быть локальной для репозитория. [Официальный Pro Git: First-Time Git Setup](https://git-scm.com/book/en/v2/Getting-Started-First-Time-Git-Setup).

Одна простая доска: **To do → In progress → Review → Done**, с отдельной видимой отметкой Blocked и причиной. Это предлагаемый workflow, не утверждение о текущей настройке YouTrack. Одновременно у каждого одна основная задача; короткая проверка или ответ reviewer не требует нового большого направления.

### Одна задача от начала до приёмки

1. Открыть **реальную** задачу YouTrack: owner, результат, проверка и зависимости понятны. Уточнить связь с FR/NFR или исследовательским вопросом.
2. Создать небольшую ветку от актуальной основной версии. В имени использовать actual issue ID, например `feature/<actual-id>-assessment-idempotency`, после реального сопоставления IDs.
3. Делать осмысленные commits по мере работы; включать actual issue ID в message. Документы и схемы также версионируются. Датасеты, большие веса, личные фото и секреты не попадают в Git вместо manifest/artifact references.
4. Открыть PR/MR: проблема, изменение, результат, проверка, ограничения и ссылка на задачу. Для ML приложить run/config/split/bundle IDs; для API — изменённые schemas/fixtures и поведение ошибки.
5. Второй участник читает diff и проверяет критерий, оставляет содержательный отзыв. Его review не заменяется автоматическим «всё хорошо» без просмотра.
6. После исправлений и приёмки объединить изменение; добавить в задачу PR/commit, отчёт или артефакт. Только затем перевести в Done.

PR позволяет обсуждать и проверять изменение до merge; это обычный механизм совместной работы, а не только финальная загрузка проекта. [GitHub: Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests).

YouTrack умеет связывать commits и PR/MR с issue IDs при настроенной VCS integration. До её проверки сохранять ссылки вручную; наличие ID в локальном CSV само по себе не включает интеграцию. Автоматические команды смены статуса из commit messages не требуются для первого простого процесса. [YouTrack: VCS Integration](https://www.jetbrains.com/help/youtrack/cloud/integration-with-version-control-systems.html).

### Минимальная трассировка

`требование / гипотеза → actual YouTrack issue → branch / commit → PR/MR + review → проверка / отчёт → milestone tag`.

В задаче хранится ссылка на PR и результат; в PR — ссылка на задачу и затронутые FR/NFR/H. В ML-отчёте — commit, config, source/split hashes, seeds и артефакт. Для сдачи tag указывает точную проверенную версию; ранее сданный tag не передвигается ради скрытого исправления. Новое исправление получает новый commit и при необходимости новый tag.

## 8. Общий Definition of Done

Задача завершена, когда её результат существует, критерий проверен указанным способом, другой участник выполнил содержательное review, документация/контракт обновлены при необходимости, а действительные ссылки на изменение и свидетельство сохранены. Если остаётся блокирующее условие, статус отражает его; `proposed`, `prepared` и `measured` не подменяют друг друга.

Для документов достаточно содержательной проверки и согласованности с пакетом. Для software нужны реальные проверки поведения. Для ML нужны сохранённые запуски и честный протокол. Для интервью и отзыва нужны состоявшиеся внешние действия. Для диагностического выпуска нужны отдельно определённые и выполненные условия валидации; готовность исследовательского отчёта не равна готовности выдавать подтверждённые диагнозы.
