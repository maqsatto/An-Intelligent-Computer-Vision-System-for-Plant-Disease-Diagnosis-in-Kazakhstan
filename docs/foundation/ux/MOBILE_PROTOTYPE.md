Создано **22 мобильных фрейма 390×844**: 12 основных экранов, 8 вариантов четырех шагов для картофеля и томата и 2 дополнительных состояния. Веб-макеты не создавались. Основной файл содержит редактируемые тексты, векторы, auto-layout, reusable components, design variables и переходы. Это дизайн-прототип, не работающее приложение и не отчет об обучении модели.

## Основные экраны и требования

| Экран | Назначение | Сценарий и приемка будущей реализации |
|---|---|---|
| 01 Главная | Начать наблюдение и вернуться к последним случаям | Понятное основное действие; история не смешивается с очередью на устройстве |
| 02 Выбор культуры | Уточнить культуру и увидеть границы поддержки | Реальный клиент использует supported manifest, а не захардкоженный список из макета |
| 03 Съемка | Один лист крупным планом | Подсказки по фокусу, свету и границам листа; камера/галерея |
| 04 Проверка фото | Предпросмотр перед отправкой | Можно переснять и исправить культуру; привязка к участку необязательна |
| 05 Анализ | Показать обработку | В реализации различаются upload и queued/running; можно перейти в историю |
| 06 Гипотеза | Показать вероятное состояние и следующий шаг | Outcome `predicted`; без обещания доказанного возбудителя и без фиктивного процента точности |
| 07 Недостаточно данных | Честно сообщить неопределенность | Outcome `inconclusive`; объяснить следующее действие |
| 08 Пересъемка | Исправить недостаточное качество | Outcome `retake_photo` или локальная проверка; не технический crash |
| 09 Без связи | Сохраненные на устройстве фотографии | Offline capture/upload queue, не offline inference; отправка после восстановления связи |
| 10 История | Найти наблюдение и его результат | Фото, культура, дата/статус; только данные владельца |
| 11 Нет поддержки культуры | Объяснить недоступность анализа до запуска | Preflight `unsupported_crop` / HTTP 422 без job; наблюдение можно сохранить без диагностики |
| 12 Обратная связь | Сохранить комментарий | Feedback не заменяет model prediction и не становится подтвержденной annotation |
| 21 Техническая ошибка | Объяснить сбой обработки | Processing status `failed`; повторить анализ или открыть историю; это не неопределенный диагноз |
| 22 Неподдержанное изображение | Объяснить ограничение типа снимка после обработки | Processing `completed`, outcome `unsupported_input`; пример неподдержанного органа, отдельный от preflight отказа культуры |

Точные ID FR/NFR, API-поля и коды ошибок берутся из `planning/REQUIREMENTS_AND_TRACEABILITY.md` и `contracts/API_CONTRACT.md`. Макет не вводит отдельную бизнес-логику.

## Проверяемые переходы

Главная → выбор культуры → съемка → preview → анализ → результат → история/новое наблюдение/feedback. Для каждой из трех культур создана собственная ветка съемки, preview, анализа и результата. После демонстрационного ожидания экран анализа переходит к условной гипотезе. Это прием прототипирования, а не измеренное время inference.

Из истории можно открыть пример неуверенного ответа, пересъемки и offline-очереди. Экран неподдержанной культуры показывает альтернативное действие. Дополнительные стартовые flows показывают техническую ошибку и неподдержанное изображение. Back возвращает в выбор культуры. Демонстрационная история статична: она не добавляет реальные записи после каждого клика. Поля заметки, выбора причины и привязки участка показывают будущую форму; ввод/хранение данных пока не реализованы. Переход RU/ҚАЗ является обозначением будущей локализации; казахская версия текстов и ее агрономическая проверка остаются задачей реализации.

Общие экраны `inconclusive` и пересъемки возвращают действие нового снимка к выбору культуры; они не подставляют пшеницу автоматически. Действие «Попробовать отправить» в статическом offline-примере ведет к анализу **первого картофельного фото очереди**. Это демонстрационная навигация; реальное приложение должно сохранять культуру каждого draft и выполнять очередь по ее данным.

**«Другая культура» и сохранение без анализа.** В реализации серверное наблюдение разрешено сохранить для **известной записи каталога** с `can_assess: false`; это запись без assessment, а не поддержка диагностики. Если вид растения еще не сопоставлен с известным `crop_id`, фото и заметку можно оставить только локальным draft до уточнения. Клиент не создает произвольный стабильный ID из свободного текста: неизвестный `crop_id` сервер отклоняет как `invalid_crop`. Ни выбор этого пункта, ни сохранение draft не запускают inference и не превращают неизвестную культуру в обучаемый класс.

## Данные макета

Все названия результатов и записи истории — **условные примеры**. Пшеница: `wheat.stripe_rust` — «Возможная жёлтая ржавчина». Картофель: `potato.early_blight` — «Возможный альтернариоз». Томат: `tomato.early_blight` — «Возможный альтернариоз». Это соответствие синтетическим примерам контракта, а не утвержденный каталог обученной модели.

Иллюстрация листа нарисована вектором и явно подписана. Она не является клиническим/фитопатологическим образцом, фотографией конкретной культуры, датасетом или Grad-CAM. Одинаковое изображение используется для демонстрации компоновки. На этапе реализации оно заменяется пользовательским фото; результат поступает только из реального проверенного bundle.

## Визуальная основа

Светлый фон и темно-зеленые основные действия, отдельные предупреждения песочного оттенка; состояние сообщается текстом вместе с цветом. Шрифт Roboto. Основные действия имеют высоту 56 px в макете. Повторяющиеся navigation, actions, status badges, rows и icons представлены экземплярами компонентов; цвета и ключевые размеры вынесены в переменные.

Это отправная точка для проверки с пользователями. Контраст, размер системного текста, screen reader, работа в ярком свете и реальные Android touch targets проверяются на устройстве. Размер Figma-фрейма не заменяет адаптивную верстку и accessibility-проверку.

## Как проверить с пользователями

Попросить человека без подсказки: создать наблюдение; объяснить смысл предварительного вывода; понять, почему ответа нет; найти фото, которое еще не отправлено. Записать места остановки, неверные ожидания и предложенные действия. Не спрашивать только «нравится ли дизайн». Результаты внести в шаблон интервью и связать с изменением требования/экрана.

## Проверка артефакта

Проведена структурная проверка сохраненных связей Figma; результат — в [FIGMA_QA.json](FIGMA_QA.json). Зафиксированы **22 экрана, 115 переходов `NAVIGATE`, 7 отдельно учитываемых взаимодействий компонентов `CHANGE_TO` и 5 различных корректных стартовых точек**. Для экранных переходов не обнаружены отсутствующие цели или переходы на тот же экран. JSON разобран, количество узлов/связей и соответствие целей существующим screen IDs проверены; component variants не смешиваются с мобильными экранами.

После финальных изменений просмотрены экспорты основных и вариантных экранов, включая `failed` и completed `unsupported_input`; видимого обрезания текста не обнаружено. Исправлены ширина кнопок, подписи условных результатов и четыре связи общего повторного снимка/offline-примера. Это проверка структуры файла и изображений. Ручной проход по всем кликам, реальный usability test, сборка React Native, работа камеры и выполнение API не проводились.
