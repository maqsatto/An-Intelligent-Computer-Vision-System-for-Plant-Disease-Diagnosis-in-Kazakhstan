# Политика данных AgroVision

**Версия документа:** 1.0, 21 октября 2026 года.  
**Область:** изображения сельскохозяйственных культур для диплома *An Intelligent Computer Vision System for Plant Disease Diagnosis in Kazakhstan*.  
**Статус:** предлагаемый протокол проекта. Он не подтверждает наличие собранного корпуса, полученных согласий, выполненного обучения или достигнутых метрик.

Связанные файлы: [каталог кандидатов](DATASET_CATALOG.md), [datasets.csv](datasets.csv). Реестр содержит сведения источников; фактический image manifest будет создан после допуска и получения файлов.

## 1. Цель и границы

Система разрабатывается для предварительной оценки видимых проблем на фотографиях сельскохозяйственных культур. Первые кандидаты пилота — пшеница, картофель и томат; кукуруза рассматривается как расширение. Поддержка объявляется для конкретных сочетаний **культура × состояние × орган × условия применения**, а не для всех болезней культуры сразу.

Публичные наборы используются для исследовательского старта и сравнения методов. Отдельный местный набор нужен для выводов о применимости к фотографиям из Казахстана. Место происхождения, условия съёмки и способ подтверждения меток должны оставаться видимыми в результатах эксперимента.

У документов и данных разные статусы:

| Статус данных | Значение | Допустимое действие |
|---|---|---|
| Кандидат | Найдена карточка/статья | Анализ описания, без заявления о фактическом составе |
| Права проверены | Зафиксирована версия и допустимый сценарий использования | Получение данных согласно условиям |
| Файлы проверены | Проверены архив, декодирование, manifest, происхождение и дубликаты | Подготовка разметки и разделения |
| Допущен к эксперименту | Утверждены метки, группы, split и протокол | Обучение/оценка в определённой роли |
| Исключён или ограничен | Обнаружены проблемы прав, меток или происхождения | Только явно разрешённое использование; причина сохраняется |

Эти статусы не заменяют статусы поддержки культур в продукте.

## 2. Допуск внешних данных

Для каждого источника ответственный за данные фиксирует оригинальную страницу, дату просмотра, автора, версию/DOI, URL получения и текст лицензии именно **данных**. Лицензия программного кода или статьи отдельно не устанавливает права изображений. Для веб-корпусов сохраняются сведения о первичных URL и индивидуальных условиях, когда они предоставлены.

Перед допуском проверяются разрешения для предполагаемых операций: хранение, обучение, преобразования, показ примеров в дипломе, передача третьей стороне и публикация файлов/производных. Условия NC/ND/SA не снимаются тем, что работа учебная. Если конкретное использование неясно, данные не допускаются в соответствующую операцию до выяснения условий. Это правило принятия решения проекта, а не универсальное толкование лицензий.

Сохраняется копия карточки/условий и контрольная сумма архива. Удалённый или изменившийся источник не должен стирать историю происхождения уже использованной версии. Набор с неизвестной лицензией остаётся кандидатом; наличие кнопки Download не меняет этот статус.

Получение данных и выполнение содержащихся в архиве программ — разные действия. Для image dataset достаточно проверить файлы изображений, разметки и метаданных; запуск постороннего кода не требуется по умолчанию.

## 3. Онтология меток

### 3.1. Основные сущности

| Поле / сущность | Назначение | Правило |
|---|---|---|
| `crop_id` | Стабильный идентификатор культуры | Человекочитаемые названия RU/KK/EN хранятся отдельно; виды/сорта не додумываются |
| `condition_id` | Стабильное состояние внутри согласованного словаря | Не строится только из совпадения строк `rust`, `spot`, `blight` |
| `condition_type` | `disease`, `pest_damage`, `abiotic`, `healthy_appearance`, `symptom`, `unresolved` | Болезнь, повреждение вредителем и симптом различаются |
| `label_granularity` | Конкретная болезнь, группа причин, симптом, видимое отсутствие симптомов | Более общая исходная метка не становится более точной при переименовании |
| `organ` | Лист, колос, стебель, плод, клубень, целое растение, неизвестно | Поддержка одного органа не распространяется на другой автоматически |
| `annotation_type` | Image label, bounding box, lesion mask, leaf mask, severity label | Схемы разметки не взаимозаменяемы |
| `label_method` | Визуальная оценка, экспертный консенсус, лабораторное подтверждение, исходная метка набора | Название метода отражает реально выполненную проверку |
| `label_status` | Предварительная, проверенная, спорная, неразрешённая | Спорные метки не скрываются внутри «чистого» теста |

Таблица сопоставления должна содержать исходные `source_label`, `source_dataset`, `source_version`, целевой ID, основание сопоставления, проверяющего и дату. Значение `unmapped` допустимо. Версия онтологии сохраняется вместе с моделью.

### 3.2. Примеры допустимых и недопустимых сведений

| Исходная метка | Допустимое действие | Ошибка, которую нужно предотвратить |
|---|---|---|
| Potato uncontrolled: `fungi` | Оставить группу грибных причин; направить на дополнительную разметку | Переименовать все фото в early blight |
| Potato uncontrolled: `virus` | Сохранить широкую категорию | Назвать конкретный вирус без подтверждения |
| Tomato dataset: `black spot` | Уточнить определение у источника/эксперта | Свести по названию с bacterial spot или target spot |
| Sunflower: `leaf scars` | `condition_type=symptom` | Представить как установленного патогена |
| Paddy: повреждение вредителем | `condition_type=pest_damage` | Посчитать отдельной инфекционной болезнью |
| `healthy` в исходном наборе | `healthy_appearance` в пределах исходной схемы | Считать доказательством отсутствия всех заболеваний |

Основания примеров: [картофель](https://data.mendeley.com/datasets/ptz377bwb8/1), [томат](https://data.mendeley.com/datasets/bpfd9cns5g/1), [подсолнечник](https://data.mendeley.com/datasets/b83hmrzth8/1), [Paddy Doctor](https://arxiv.org/html/2205.11108v2).

### 3.3. Неопределённость и смешанные случаи

`Unknown`, неподдерживаемая культура, неподдерживаемый орган, плохое качество и недостаточность признаков — состояния обработки запроса, а не синонимы `healthy_appearance`. Низкая уверенность среди известных болезней не даёт права объявлять растение здоровым.

Несколько видимых проблем сохраняются в полном описании случая. Если первый эксперимент одноярлычный, фиксируется правило выбора основной метки и ограничения такого упрощения. Смешанные и спорные случаи можно исключить из supervised train с указанной причиной и отдельно использовать для оценки отказа. Нельзя превращать отсутствие второй метки в доказанное отсутствие второй проблемы.

Bounding box листа, маска поражения, процент повреждения листовой поверхности и агрономическая тяжесть — разные величины. Доля поражения считается относительно подходящей маски листа, если обе маски действительно размечены. Grad-CAM и площадь box не заменяют такую разметку. Порядковая шкала тяжести хранится с `severity_scheme`; её нельзя без основания переименовать в стадии болезни или проценты.

## 4. Image manifest и связанные реестры

Manifest содержит **одну строку на изображение**, а таблица аннотаций — столько записей, сколько требуется для объектов/состояний. Отдельный `case_id` объединяет несколько фотографий одного диагностического обращения. Один файл не равен одному независимому растению.

### 4.1. Минимальные поля manifest

| Группа | Поля | Смысл |
|---|---|---|
| Идентичность | `image_id`, `case_id`, `relative_path`, `sha256` | Неизменяемый ID, место хранения и побайтовая идентичность |
| Происхождение | `source_dataset`, `source_version`, `source_image_id`, `source_url`, `downloaded_at` | Откуда взят конкретный файл |
| Права | `license_id`, `license_evidence_ref`, `allowed_use_status`, `consent_id` | Ссылка на условия или локальное согласие; контакт не хранится здесь |
| Технические свойства | `width_px`, `height_px`, `file_format`, `modality`, `capture_device_group` | RGB/IR/UAV/сканер различаются; отсутствующее значение не выдумывается |
| Контекст | `country`, `region_coarse`, `farm_id`, `plot_id`, `plant_id`, `leaf_id`, `capture_session_id`, `captured_at` | Псевдонимы и известные групповые связи |
| Родство | `parent_image_id`, `transform_id`, `dedup_cluster_id`, `split_group_id` | Исходник, производное преобразование и единица разделения |
| Метки | `crop_id`, `ontology_version`, `annotation_ref`, `label_status`, `reviewer_id`, `label_method` | Ссылка на полную разметку и её проверку |
| Качество | `quality_status`, `quality_issue`, `exclusion_reason` | Плохой снимок не исчезает без причины из аудита |
| Эксперимент | `dataset_release_id`, `split`, `split_protocol_id`, `audit_status` | Фиксированная версия и роль: train/validation/test/quarantine |

Для неизвестных идентификаторов используется пустое значение с причиной в метаданных. Нельзя заполнять отсутствующий `plant_id` номером файла, создавая видимость независимости. Точные координаты, контакты и документы согласия хранятся отдельно с ограничением доступа.

### 4.2. Связанные записи

- **Реестр источников:** версия, условия, ссылки, контрольная сумма архива, результаты допуска.
- **Реестр случаев:** культура, видимые симптомы, контекст, фотографии, исходная и итоговая оценка.
- **Аннотации:** исходная метка, целевая метка, box/mask при наличии, метод, проверяющие, разногласия.
- **Согласия:** участник/правообладатель, версия текста, дата, отдельные разрешённые цели и отозванные разрешения.
- **Протокол эксперимента:** список файлов/групп, ontology version, split seed, настройки отбора, признаки доступные модели.

Пример записи в manifest должен оставаться явно синтетическим до появления данных. В итоговый корпус нельзя добавлять демонстрационную строку, как будто фотография действительно собрана.

## 5. Дубликаты, производные и разделение

### 5.1. Последовательность до обучения

1. Зафиксировать исходные архивы и manifest. Исходники хранить отдельно от подготовленных файлов.
2. Проверить декодирование, технические свойства и exact duplicates по SHA-256.
3. Найти кандидаты near-duplicates через perceptual hash/сходство, имена и исходные URL. Порог — инструмент отбора на проверку, а не самостоятельное доказательство дублирования.
4. Просмотреть сомнительные пары и объединить подтверждённые семьи: один лист, растение, серия, исходник и его crops/повороты/фоны/patches.
5. Проверить пересечения **между всеми источниками**, включая публичные mirrors. Названия разных датасетов не доказывают независимость.
6. Сформировать `split_group_id` и разделить группы согласно протоколу. Только затем создавать аугментации train.
7. Зафиксировать список train/validation/test и его хеш. До сравнения моделей отдельно проверить отсутствие пересечения групп.

Практические основания: PlantVillage содержит варианты одних исходников и сведения `leaf_grouping` ([репозиторий](https://github.com/spMohanty/PlantVillage-Dataset)); CD&S описывает производные фоны ([статья](https://arxiv.org/html/2110.12084v1)); ячмень состоит из фрагментов исходных листьев ([карточка](https://data.mendeley.com/datasets/4ny92p2r8f/1)).

### 5.2. Три разных контура оценки

| Контур | Как разделять | Какой вывод допустим |
|---|---|---|
| Воспроизведение публичного benchmark | Официальный split, если он известен; все обнаруженные нарушения описать | Сопоставление с публикацией на этом протоколе |
| Проверка переноса между источниками | Независимые источники/сессии и общий согласованный словарь; аудит межкорпусных дубликатов | Устойчивость к указанной смене домена |
| Казахстанский полевой тест | Отложенные хозяйства/участки/сессии, по возможности иной период и устройства; закрыть от настройки | Качество в описанных локальных условиях |

Все фотографии одного случая и все производные остаются в одной части. Для локального теста предпочтителен holdout по хозяйствам или иным достаточно независимым группам. Если это оставляет слишком мало случаев определённого класса, результат отмечается как недостаточный; группировку нельзя ослаблять только ради красивой метрики.

При неполных метаданных степень независимости ограничена. Тогда допустим консервативный split по источнику/очевидным сериям и явная оговорка. Случайное деление файлов с неизвестными связями не называется проверкой на новых хозяйствах.

Validation используется для выбора модели, preprocessing, температуры/калибровки и порога отказа. Test не используется для выбора классов, параметров аугментации или порогов. Если утечка обнаружена после просмотра тестовых результатов, фиксируются нарушение и пересмотр протокола; для нового подтверждающего вывода нужен независимый тест.

### 5.3. Аугментации

Разрешённые преобразования применяются только к train после split; предпочтительна генерация во время обучения. Они не увеличивают число независимых наблюдений. Сохраняется связь с исходником и версия преобразования.

Повороты, обрезка, цвет и замена фона должны сохранять диагностические признаки. Сильное изменение цвета может менять вид симптомов; выбор интенсивности проверяется на validation. Для масок/boxes геометрические преобразования синхронны. В validation/test допустим заранее описанный одинаковый preprocessing, но не создание «дополнительных тестовых примеров» из одного листа для увеличения n.

## 6. Сбор местных данных

### 6.1. План до выезда

Команда согласует с партнёром культуры, регионы, органы и кандидаты состояний. Для каждого класса планируются разные хозяйства/сессии, фон, освещение, устройства и выраженность симптомов. Конкретное количество случаев и пороги допуска устанавливаются **до** итогового теста в протоколе оценки; универсального научного минимума «N фото на класс» здесь не заявляется.

Нужно собирать не только ярко выраженные известные болезни: важны визуально нормальные растения, похожие абиотические повреждения, неподдерживаемые состояния, смешанные признаки и неудачные снимки. Это позволяет проверить поведение при отказе. Окружающие растения с одного участка не считаются полностью независимыми только из-за разных файлов.

### 6.2. Протокол случая

Для одного растения целесообразно получить общий вид и близкие виды симптомов, сохраняя `case_id` и `plant_id`. Число фотографий — свойство сценария, а не способ умножить тестовую выборку. Записываются дата/сессия, культура, орган, стадия роста при известности, способ съёмки, краткие наблюдения и применённые обработки при согласии участника.

Видимая оценка специалиста и лабораторное подтверждение обозначаются разными методами. Если лабораторного результата нет, его нельзя подразумевать словом «подтверждено». Сначала специалист формирует оценку по согласованному протоколу; ответ модели не должен служить основанием для метки теста. Спорные случаи рассматриваются повторно и остаются спорными, пока не получено достаточное основание.

Многоснимочный протокол имеет научный прецедент: исследование Nuru оценивало влияние числа осматриваемых листьев на диагностику маниоки ([Mrisho et al., 2020](https://www.frontiersin.org/journals/plant-science/articles/10.3389/fpls.2020.590889/full)). Это мотивирует проверку сценария, но не перенос конкретного результата на другие культуры.

### 6.3. Согласие и обращение с данными

До получения материала участнику сообщаются цель диплома, какие данные собираются, кто будет иметь доступ, как долго они предполагаются к хранению, способ обращения по вопросам/отзыву и отдельные варианты использования. Реальные имена ответственных и сроки должны быть заполнены командой до сбора; этот документ не является полученным согласием.

Разрешения фиксируются отдельно:

| Цель | Что согласовывается |
|---|---|
| Внутреннее исследование | Хранение изображений и метаданных, разметка и оценка в команде |
| Обучение модели | Использование разрешённых примеров в тренировочных выборках |
| Передача внешнему сервису | Конкретный API/поставщик и передаваемые сведения; не следует из общего согласия на диплом |
| Показ в дипломе/защите | Изображения и разрешённая степень описания места/хозяйства |
| Открытая публикация | Отдельное разрешение на выдачу файлов или выбранную лицензию |

Отказ от публикации не означает автоматический отказ от внутреннего исследования, если цели согласованы отдельно. Фермер должен иметь право предоставлять фотографию; требуется учитывать также автора снимка и права хозяйства. В кадре не нужны лица, номера документов или идентифицирующие вывески. Ненужные EXIF и точные GPS удаляются из рабочих/публичных копий; оригиналы при необходимости хранятся ограниченно.

Контакты и формы согласия отделены от image manifest. Публичный репозиторий содержит код, схемы, агрегаты и разрешённые примеры; приватные изображения/координаты/согласия в Git не помещаются. Доступ к локальному корпусу выдаётся по роли; выдача внешнему API фиксируется отдельно.

При отзыве разрешения ID отмечается как исключённый для будущего использования и удаляется из доступных рабочих копий в рамках согласованной процедуры. Обещать автоматическое удаление влияния примера из уже обученных весов нельзя: последствия для переобучения, публикации и ранее выданных копий должны быть заранее объяснены и документированы.

## 7. Критерии выпуска поддержки

| Статус сочетания культура–состояние | Требуемое основание | Как описывать пользователю |
|---|---|---|
| В каталоге | Есть справочная запись | Диагностическая поддержка не заявляется |
| Исследовательский | Обучение/оценка на внешних данных документированы | Экспериментальная функция без локального подтверждения |
| Пилотный | Есть ограниченная локальная проверка, партнёр и понятные границы | Указать культуры, состояния, органы, регион/условия и ограничения |
| Поддерживаемый в заданных условиях | Выполнены заранее согласованные per-class критерии на отдельном местном тесте, проверены отказ и сценарии пользователя | Заявлять только проверенные условия применения |

Для решения о выпуске нужны per-crop/per-class precision, recall, F1, матрица ошибок и число независимых случаев. Macro-F1 дополняется анализом редких классов. Для механизма отказа сообщаются доля принятых запросов (coverage), ошибки среди принятых, причины отказа и поведение на неподдерживаемых/плохих/смешанных снимках.

Доверительные интервалы и n должны учитывать независимые случаи/группы, а не количество аугментаций. Порог confidence не объявляется вероятностью правильного диагноза без проверки калибровки. Высокая общая accuracy не компенсирует провал отдельной поддерживаемой болезни.

Решение фиксируется записью: версия данных, онтологии и модели; область поддержки; протокол и результаты; известные ошибки; согласующие роли; дата. Пока эти сведения не получены, статус не повышается. Числовые критерии нельзя подбирать после ознакомления с test ради прохождения допуска.

## 8. Контроль перед экспериментом и публикацией

| Проверка | Требуемое свидетельство |
|---|---|
| Версия и происхождение | Реестр источников, URL/DOI, хеш архива и конкретных файлов |
| Права | Условия изображений и разрешённые операции; согласия для локальных данных |
| Метки | Версия словаря, исходные метки, проверка спорных сопоставлений |
| Независимость | Отчёт exact/near-duplicate, семей производных и групп split |
| Локальность | Реальные метаданные сбора Казахстана; неизвестные поля явно отмечены |
| Оценка | Замороженный протокол и test, per-class результаты, неопределённость и ограничения |
| Публикация | Только разрешённые файлы/агрегаты, отсутствие контактов и точных частных координат |

На дату создания политики перечисленные свидетельства предстоит получить. Наличие готового шаблона или каталога кандидатов не означает прохождение этих проверок.
